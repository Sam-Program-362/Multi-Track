# Audit — prayer time intelligence & annual mosque schedules

Date: 2026-11-15 · Branch: `arena/b3e97a09-multi-track` · Base: `main` @ `4733675`

This audit answers three questions before any code was changed: **what does the repository
actually do today**, **is that maths right**, and **what is genuinely missing** for the
"enter the mosque schedule once, follow it all year" requirement.

## 2. What is correct (verified)

The solar engine (`src/lib/prayer.ts`, byte-identical to `android/src/lib/prayer.ts`) was
compared against [`adhan`](https://github.com/batoulapps/adhan-js), an independent
implementation of the same conventions, for **7 cities × 4 dates × 5 authorities** with
matching high-latitude rules:

| Prayer | Max absolute difference |
| --- | --- |
| Sunrise | 0 min |
| Dhuhr | 1 min |
| Asr | 1 min (both shadow factors) |
| Maghrib | 1 min |
| Fajr | 0 min (latitudes ≤ 48°) |
| Isha | 1 min (latitudes ≤ 48°; Umm al-Qura minute-based verified separately) |

Also verified:

* **Asr** shadow factor 1 (Standard) vs 2 (Hanafi) matches the reference implementation.
* **Umm al-Qura Isha** = 90 min after Maghrib, 120 min in Ramadan (documented intentional
  deviation: the reference library does not model the Ramadan extension).
* **Elevation** raises the apparent horizon (`0.833° + 0.0347°·√h`): 1600 m ≈ +5–7 min on
  Maghrib, symmetrical on Sunrise.
* **High-latitude rules** (`angle`, `seventh`, `middleOfNight`) match their reference
  counterparts to ≤ 3 min at London on the solstice.
* **Δuser algebra**: capture with midnight wrap, ±180 min clamp, projection to any date,
  step quantisation (`ceil(m/S)·S`), fixed clock short-circuit, DST-safe zone sampling.
* **Legacy recovery**: v1 rows that only stored a clock time are converted to Δuser against
  the astronomical baseline instead of being re-pinned every read.

## 3. What was mathematically or architecturally wrong / risky

1. **A single prayer offset was overloaded with mosque policy.** `Δuser` was implicitly
   asked to represent the congregation delay, the mosque board rounding *and* terrain. Those
   are different quantities: a jamaat delay is not an astronomical adjustment, and changing
   it must not move the azan.
2. **No annual/seasonal model at all.** Only three per-prayer modes existed (auto, stepped,
   fixed). A mosque that publishes a handful of dated jamaat changes per year had no way to
   express it, and the UI offered no place to record it.
3. **No jamaat concept in the data model.** `PrayerPref` had one time per prayer, so the
   Azan vs Jamaat distinction the brief requires could not be represented, let alone shown.
4. **`elevationMeters` / `highLatitudeRule` existed only in TypeScript types.** The engine
   supported both, but nothing persisted or exposed them, so they were dead capability.
5. **The write path was untestable.** `PUT /api/prayers` mixed HTTP, Drizzle and calibration
   algebra in one function with no seam for tests; the repository had no test suite at all.
6. **High-latitude twilight at ~51.5° in late May legitimately produces Isha after
   midnight.** An earlier "ordering" assumption in the UI tests was wrong, not the engine —
   the corrected invariant unwraps past midnight.

| Requirement | Status after this branch |
| --- | --- |
| Five prayers, established authorities, Fajr/Isha angles, Asr 1/2, Maghrib refraction | Already correct, now numerically validated |
| Azan vs Jamaat separated end-to-end (data, UI, reminders) | **Added** |
| Jamaat policy: none / constant delay / fixed clock / dated seasonal table | **Added** |
| Seasonal table from *sufficient* data, no invented pattern from one sample | **Added** with explicit limitation handling |

| Published-timetable import (PDF/CSV/OCR) | **Not added** — out of scope for this branch; see "Remaining limitations" |

## 5. Honest limitations

* One entered jamaat time is treated as a **fixed clock** (or a constant delay), never
  stretched into a yearly curve. A mosque that changes its board monthly needs the seasonal
  table; the app says so in the editor instead of pretending.
* High-latitude conventions are a genuine boundary: a twilight angle within a fraction of a
  degree of the maximum solar depression can be declared "unreachable" by one convention and
  "reachable" by another. The app exposes the choice and documents the default bands.
* The comparison against `adhan` is an independent implementation check, not a specific
  mosque's published board. Verifying against a real printed timetable requires importing it
  (not implemented here).
